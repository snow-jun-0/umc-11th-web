# 화면을 보고 테이블을 그리는 법 — ERD 설계 기초

> **한 줄 요약** — 화면에 보이는 모든 것은 어딘가에 저장되어 있다. ERD 설계는 "이 화면을 그리려면 무엇이 저장돼 있어야 하나"를 역산하는 작업이다.

## 0. 프론트엔드가 왜 이걸 보나

ERD는 백엔드 영역이라고 생각했는데, 투겟 하면서 느낀 게 있다.
**API 응답 모양이 이상하다고 느껴질 때, 그 원인은 대부분 테이블 구조에 있었다.**

- 리스트에 매번 작성자 정보가 통째로 딸려오는 이유
- 좋아요 개수를 가져오려면 별도 요청을 해야 하는 이유
- "이 필드는 null일 수 있어요"라는 말이 나오는 이유

ERD를 읽을 수 있으면 백엔드와의 대화가 "이렇게 주세요"에서 "이건 이래서 어렵겠네요"로 바뀐다.
프론트 입장에서 이게 제일 큰 실익이다.

## 1. RDB — 왜 표를 쪼개나

RDB는 데이터를 2차원 표에 저장하고 표끼리 관계를 정의한다.

| 용어 | 다른 이름 | 뜻 |
|---|---|---|
| 테이블 | Entity | 하나의 주제로 모은 표 |
| 열 | Column / Attribute | 저장할 항목과 규격 |
| 행 | Row / Record | 실제 데이터 1건 |
| 스키마 | — | 열 구성·타입·제약조건의 명세 |

### 쪼개지 않으면 생기는 일

주문 표 하나에 사용자 정보까지 다 넣는다고 해보자.

```
[ orders — 다 합친 경우 ]
id │ user_name │ phone         │ item
───┼───────────┼───────────────┼────────
 1 │ 준영      │ 010-1111-2222 │ 키보드
 2 │ 준영      │ 010-1111-2222 │ 마우스
 3 │ 준영      │ 010-1111-2222 │ 모니터

→ 전화번호를 바꾸면?  3행을 전부 수정해야 한다.
→ 하나라도 놓치면?    "진짜 번호가 뭔데?" 상태가 된다.
```

```
[ 분리한 경우 ]
users                        orders
id │ name │ phone            id │ user_id │ item
───┼──────┼──────────────    ───┼─────────┼────────
 1 │ 준영 │ 010-1111-2222     1 │    1    │ 키보드
                              2 │    1    │ 마우스
                              3 │    1    │ 모니터

→ 전화번호는 한 곳에만 있다. 한 번만 고치면 끝.
```

이걸 **단일 진실 공급원(SSOT)** 이라고 부르고, 이렇게 나누는 작업이 **정규화**다.

### RDB를 기본값으로 쓰는 이유 4가지

**① 중복 제거** — 위에서 본 것.

**② 무결성을 DB가 강제** — 서버 코드에 버그가 있어도 DB가 마지막에 막는다.

| 종류 | 막아주는 것 |
|---|---|
| 도메인 무결성 | 나이 컬럼에 문자열, 필수 컬럼에 NULL |
| 개체 무결성 | PK 중복, 이미 가입된 이메일 재가입 |
| 참조 무결성 | 존재하지 않는 회원의 주문 생성 (고아 데이터) |

**③ ACID 트랜잭션** — 결제처럼 여러 단계가 전부 성공해야 의미가 있는 작업.

```
결제 요청
  ├─ 1. 잔액 차감
  ├─ 2. 주문 생성
  └─ 3. 재고 감소

2번에서 서버가 죽으면?
→ 트랜잭션이 없으면: 돈만 빠지고 주문은 없음 😱
→ 트랜잭션이 있으면: 전부 되돌림 (원자성)
```

| | 뜻 |
|---|---|
| Atomicity (원자성) | 전부 성공 아니면 전부 취소 |
| Consistency (일관성) | 규칙이 깨진 상태로 끝나지 않음 |
| Isolation (격리성) | 동시 요청끼리 간섭하지 않음 |
| Durability (지속성) | 커밋된 건 전원이 나가도 남음 |

**④ JOIN** — 쪼개놨어도 한 줄로 합쳐서 가져올 수 있다.

## 2. SQL vs NoSQL

| | RDB (SQL) | NoSQL |
|---|---|---|
| 구조 | 정해진 스키마의 표 | key-value / document / graph |
| 스키마 변경 | 마이그레이션 필요 | 유연 |
| 관계 질의 | JOIN으로 강력 | 어렵거나 앱에서 처리 |
| 확장 | 주로 수직(스케일 업) | 수평 확장 유리 |
| 중복 | 정규화로 최소화 | 중복 전제 (수정 이상 위험) |
| 대표 | MySQL, PostgreSQL | MongoDB, Redis, DynamoDB |

**둘 중 하나를 고르는 문제가 아니다.** 실무에서 흔한 조합은
메인 데이터는 RDB, 캐시·세션·랭킹 같은 건 Redis. 목적에 따라 섞어 쓴다.

## 3. ERD 그리기 — 요구사항에서 테이블까지

### 언제 그리나

**와이어프레임이 나오면 바로.** 화면이 확정되어야 저장할 데이터가 보인다.
기획 → 디자인(WF) → ERD → 구현 순서가 자연스러운 이유다.

### 설계 순서

```
1. 요구사항/와이어프레임에서 "저장돼야 할 명사" 뽑기   → 테이블 후보
2. 각 테이블에 들어갈 항목 정하기                      → 컬럼
3. 타입과 제약조건 정하기                              → NOT NULL, UNIQUE, enum
4. 테이블끼리의 관계 연결                              → PK / FK, 1:N, N:M
5. 다대다는 중간 테이블로 풀기
```

### 지켜야 할 컨벤션

- 네이밍 스타일 하나로 통일 (`snake_case` 권장)
- PK 이름은 `테이블명 + _id` 형태로 통일 (`user_id`, `book_id`)
- PK 타입은 확장성 고려해 `BIGINT AUTO_INCREMENT` (UUID 전략이면 `VARCHAR`)

## 4. 관계 — 1:N과 N:M

### 1:N — FK를 "N쪽"에 둔다

```
users (1)                    orders (N)
┌──────────────┐            ┌──────────────────┐
│ user_id PK   │◄───────────│ order_id  PK     │
│ name         │            │ user_id   FK     │
│ phone        │            │ item             │
└──────────────┘            └──────────────────┘

"한 사용자가 여러 주문을 가진다"
→ FK(user_id)는 주문 쪽에 들어간다.
```

**외우는 법: 화살표는 항상 "많은 쪽"에서 "하나인 쪽"을 가리킨다.**

### N:M — 중간 테이블이 필요하다

```
❌ 중간 테이블 없이:
books
id │ title  │ hashtags
───┼────────┼──────────────────
 1 │ 책A    │ "IT,입문,베스트"    ← 한 칸에 여러 값 (1정규형 위반)

→ "입문 태그 달린 책 찾기"가 문자열 검색이 된다. 태그명이 바뀌면 전부 수정.
```

```
✅ 중간 테이블로:

books              book_hashtags              hashtags
┌──────────┐       ┌──────────────────┐       ┌────────────┐
│ book_id  │◄──────│ book_hashtag_id  │──────►│ hashtag_id │
│ title    │       │ book_id      FK  │       │ name       │
└──────────┘       │ hashtag_id   FK  │       └────────────┘
                   └──────────────────┘

N:M 하나 = 1:N 두 개
```

**N:M이 보이면 중간 테이블**, 이건 거의 기계적으로 적용된다.

판별법: 양쪽에서 문장을 만들어본다.
- "한 책에 여러 태그가 붙는다" ✔
- "한 태그가 여러 책에 붙는다" ✔
- 둘 다 참 → N:M → 중간 테이블

좋아요, 대여, 찜하기, 팔로우 — 전부 같은 패턴이다.

### 중간 테이블의 숨은 이득

좋아요를 `books.like_count` 숫자 하나로 관리하면 당장은 편하다.
그런데 나중에 **"차단한 사용자의 좋아요는 제외"** 같은 요구가 들어오면 답이 없다.
중간 테이블(`book_likes`)로 두면 "누가 눌렀는지"가 남아있어서 조건을 걸 수 있다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 카운트 컬럼 | 조회 빠름 | 누가 눌렀는지 모름, 정합성 깨지기 쉬움 |
| 중간 테이블 | 유연, 정합성 | 집계 시 COUNT 필요 |

보통 중간 테이블로 두고, 성능이 정말 문제가 되면 그때 카운트 컬럼을 **추가로** 둔다(비정규화).

## 5. Soft Delete — `deleted_at`은 왜 있나

```
users
┌────────────────┐
│ user_id   PK   │
│ name           │
│ created_at     │
│ updated_at     │
│ deleted_at     │  ← NULL이면 활성, 값이 있으면 탈퇴
└────────────────┘
```

| | 동작 | 문제 |
|---|---|---|
| Hard Delete | 행을 진짜 삭제 | 복구 불가, 이 사람이 쓴 글도 FK 때문에 같이 날아감 |
| Soft Delete | `deleted_at`에 시각 기록 | 조회할 때마다 조건을 걸어야 함 |

**플로우**

```
1. 탈퇴 요청
2. deleted_at = NOW()
3. 이후 모든 조회에 WHERE deleted_at IS NULL 추가
4. 유예 기간(예: 30일) 지나면 스케줄러가 실제 삭제
```

탈퇴 복구, 휴지통, 탈퇴자가 남긴 게시글 유지 — 이런 기능이 하나라도 있으면 Soft Delete가 사실상 필수다.

⚠️ 프론트 입장에서 알아두면 좋은 것: Soft Delete를 쓰면 **탈퇴한 사용자의 글이 "알 수 없음"으로 남는 UI**가 필요해진다. 이건 디자인 단계에서 챙겨야 하는 부분이다.

## 6. 완벽한 ERD를 그리려 하지 말 것

이번 주차에서 제일 마음에 남은 조언.

> 프로젝트를 하다 보면 ERD는 반드시 바뀐다.
> "완벽한 설계"에 시간을 쓰기보다 **"이 구조로 구현이 되나?"** 에 초점을 맞춰라.

그리고 제약조건은 **혼자 정하지 말 것.** "닉네임 중복 허용인가?", "전화번호 필수인가?" 같은 건
PM에게 물어봐야 하는 질문이다. 임의로 정해놓고 나중에 바꾸면 양쪽 다 곤란해진다.

## 셀프 체크

<details>
<summary>1. 주문 표에 사용자 이름과 전화번호를 같이 넣으면 뭐가 문제인가?</summary>

같은 값이 주문 건수만큼 중복 저장된다. 사용자가 전화번호를 바꾸면 모든 행을 고쳐야 하고,
일부만 고쳐지면 어느 값이 진짜인지 알 수 없는 불일치가 생긴다(수정 이상).
사용자 정보는 users 테이블 한 곳에만 두고 orders는 FK로 참조해야 한다.
</details>

<details>
<summary>2. 1:N에서 FK는 어느 쪽에 두나?</summary>

N쪽(많은 쪽)에 둔다. 한 사용자가 여러 주문을 가지면 `orders.user_id`가 FK가 된다.
반대로 두면 한 컬럼에 여러 주문 ID를 넣어야 해서 1정규형이 깨진다.
</details>

<details>
<summary>3. N:M 관계를 중간 테이블 없이 만들면?</summary>

한 칸에 여러 값을 넣게 되어 제1정규형을 위반한다.
검색·수정이 문자열 처리가 되고 참조 무결성도 보장되지 않는다.
중간 테이블을 두면 N:M이 1:N 두 개로 분해되어 정상적으로 표현된다.
</details>

<details>
<summary>4. 트랜잭션의 원자성이 없으면 결제에서 무슨 일이 생기나?</summary>

잔액 차감은 성공했는데 주문 생성 단계에서 실패하면, 돈만 빠지고 주문은 없는 상태로 남는다.
원자성은 이런 중간 실패 시 전부 시작 전 상태로 되돌린다.
</details>

<details>
<summary>5. <code>deleted_at</code> 컬럼을 두는 이유는?</summary>

Soft Delete를 위해서. 행을 실제로 지우지 않고 삭제 시각만 기록하면
탈퇴 복구가 가능하고, 그 사용자를 참조하던 게시글·댓글도 함께 사라지지 않는다.
대신 모든 조회 쿼리에 `WHERE deleted_at IS NULL` 조건이 필요하다.
</details>

<details>
<summary>6. 좋아요를 카운트 컬럼 하나로 관리했을 때의 한계는?</summary>

누가 눌렀는지가 남지 않아서 "특정 사용자 제외" 같은 조건을 걸 수 없고,
내가 좋아요를 눌렀는지 여부도 알 수 없다. 증감 도중 실패하면 정합성도 깨진다.
중간 테이블로 두면 이런 요구사항을 모두 처리할 수 있다.
</details>
