# 요청 한 번에 무슨 일이 일어나는가 — 클라이언트·서버와 HTTP

> **한 줄 요약** — 클라이언트/서버는 *역할*의 구분이고 프론트/백엔드는 *코드 영역*의 구분이다. 둘은 다른 축이라 "프론트엔드는 서버가 없다"는 말은 성립하지 않는다.

## 0. 내가 헷갈렸던 지점부터

프론트엔드를 하면서도 "서버 개발자 = 백엔드"라고 뭉뚱그려 생각했었다.
그런데 내가 만든 React 앱도 결국 어딘가에 **배포**되고, 사용자의 브라우저는 그 어딘가로 파일을 **요청**한다.
그 "어딘가"가 서버다. 즉 프론트엔드도 서버에 올라간다.

```
              [ 역할 축 ]
   클라이언트  ←──────────→  서버
   (요청하는 쪽)            (응답하는 쪽)

              [ 코드 축 ]
   프론트엔드  ←──────────→  백엔드
   (화면/UI 코드)           (로직/DB 코드)

   → 두 축은 교차한다.
     프론트엔드 코드도 "웹 서버"에 배포되어 클라이언트에게 전달된다.
```

| | 무엇을 나누나 | 핵심 질문 |
|---|---|---|
| 클라이언트 / 서버 | 통신에서의 역할 | 누가 요청하고 누가 응답하나? |
| 프론트엔드 / 백엔드 | 코드의 목적 | 화면을 그리는 코드인가, 데이터를 다루는 코드인가? |

서버가 "24시간 켜져 있는 컴퓨터"인 이유도 단순하다. 요청이 언제 올지 모르니까 항상 대기해야 한다.

## 1. API — 왜 DB를 직접 안 보나

API는 Application Programming **Interface**다. 핵심은 인터페이스, 즉 **접점**.

- UI: 사람 ↔ 프로그램의 접점 (버튼, 입력창)
- API: 프로그램 ↔ 프로그램의 접점 (정해진 규격의 요청/응답)

내가 이해한 API의 존재 이유는 두 가지다.

1. **프론트가 몰라도 되게** — DB 테이블이 몇 개인지, 조인이 어떻게 걸려 있는지 알 필요 없이 필요한 형태의 데이터만 받는다.
2. **백엔드가 통제할 수 있게** — 노출 범위를 백엔드가 정한다. 권한 없는 데이터는 애초에 응답에 안 들어간다.

투겟 할 때 API 명세서가 먼저 나와야 프론트가 움직일 수 있었던 이유가 이거였다.
명세서는 "이 주소로 이렇게 요청하면 이런 모양이 온다"는 **계약서**고, 계약이 있어야 양쪽이 병렬로 개발할 수 있다.

## 2. URL 분해하기

```
https :// api.example.com : 443 / users/42/orders ? status=paid&limit=20
└─┬──┘    └──────┬──────┘  └┬─┘  └──────┬───────┘  └─────────┬────────┘
  │              │          │           │                    │
  │              │          │           │                    └─ 쿼리 스트링: 조건
  │              │          │           └───────────────────── 경로: 어떤 자원
  │              │          └───────────────────────────────── 포트: 어느 프로그램
  │              └──────────────────────────────────────────── 호스트: 어느 컴퓨터
  └─────────────────────────────────────────────────────────── 프로토콜: 어떤 규칙
```

### 프로토콜

| | 특징 | 쓰는 곳 |
|---|---|---|
| HTTP | 평문 전송, 요청이 있어야 응답 | (지금은 거의 안 씀) |
| HTTPS | TLS로 암호화 + 서버 신원 검증 | 실서비스 표준 |
| WS / WSS | 연결을 유지하는 양방향 | 채팅, 실시간 알림 |

HTTP의 구조적 한계는 **서버가 먼저 말을 걸 수 없다**는 것이다.
그래서 실시간이 필요하면 두 가지 선택지가 생긴다.

```
[ 폴링 ]  클라 → "새 거 있어?" → 서버   (1초마다)
          클라 ← "없어"        ← 서버
          클라 → "새 거 있어?" → 서버
          클라 ← "없어"        ← 서버      ... 대부분이 헛요청

[ 웹소켓 ] 클라 ⟷ 연결 수립 (1회)
          클라 ⟷════════════⟷ 서버
                  이후 양쪽 다 아무 때나 전송 가능
```

폴링은 실시간을 **흉내**만 낼 뿐이고, 변화가 없어도 요청 비용은 그대로 든다.

### 호스트와 DNS

```
"api.example.com" 입력
      ↓
DNS 서버에 질의: "이 이름의 IP가 뭐야?"
      ↓
"93.184.x.x 야"
      ↓
그 IP로 TCP 연결
```

도메인은 IP에 붙인 사람용 별명이고, DNS는 그 별명을 실제 주소로 바꿔주는 번역기다.

**`localhost` / `127.0.0.1`** 은 "내 컴퓨터 자신"을 가리키는 예약된 주소다.
패킷이 네트워크로 나가지 않고 OS 내부에서 되돌아온다(루프백). 개발 중인 서버를 외부에 노출하지 않고 테스트할 수 있는 이유다.

### 포트

IP가 건물 주소라면 포트는 호실 번호다. 서버 컴퓨터 한 대에서 여러 프로그램이 동시에 돌기 때문에 구분이 필요하다.

| 포트 | 쓰임 |
|---|---|
| 22 | SSH |
| 80 | HTTP |
| 443 | HTTPS |
| 3000 / 5173 | 로컬 개발 서버 (Node, Vite 등) |
| 3306 | MySQL |

`https://example.com`에 `:443`이 안 보이는 건 안 쓰는 게 아니라 브라우저가 **기본값이라 생략**해서 보여주는 것이다. 직접 `:443`을 붙여도 똑같이 열린다.

### 경로 vs 쿼리 스트링

이 둘의 구분이 REST API를 읽을 때 제일 실용적인 지식이었다.

```
/users/42           ← 대상을 특정한다        (Path)
/users?role=admin   ← 목록을 걸러낸다        (Query)
```

| | 언제 쓰나 | 예시 |
|---|---|---|
| Path Variable | 자원 하나를 콕 집을 때 | `/posts/17` |
| Query String | 필터 / 정렬 / 페이지네이션 | `/posts?sort=new&page=2` |

**판단 기준**: 그걸 빼면 "무엇을 달라는 건지"조차 모르겠다 → Path. 빼도 의미는 통하는데 범위만 넓어진다 → Query.

## 3. 요청 → 응답 한 사이클

```
1. 요청   브라우저가 URL + Method + (헤더/바디)를 만들어 전송
             ↓
2. 처리   서버가 라우팅 → 비즈니스 로직 실행 → DB 조회/수정
             ↓
3. 응답   상태 코드 + JSON 바디를 담아 회신
             ↓
4. 렌더   클라이언트가 JSON을 받아 화면 구성
```

서버가 보내는 건 **디자인이 아니라 데이터**다.
네이버 검색창에 글자를 칠 때마다 네트워크 탭에 자동완성 요청이 찍히는데, 응답을 열어보면 예쁜 드롭다운이 아니라 추천어 배열만 들어있다. 그걸 드롭다운으로 그리는 건 전부 프론트 몫이다.

이게 프론트엔드가 하는 일의 정의이기도 하다. **데이터를 받아서 사람이 볼 수 있는 형태로 번역하는 것.**

## 4. HTTP Method — 주소는 명사, 메서드는 동사

```
과거식:  POST /users/create
         POST /users/delete

현재식:  POST   /users      ← 같은 주소, 다른 동사
         DELETE /users/42
```

| Method | 하는 일 | CRUD | 멱등성 |
|---|---|---|---|
| GET | 조회 | Read | O |
| POST | 생성 | Create | **X** |
| PUT | 전체 교체 | Update | O |
| PATCH | 부분 수정 | Update | X |
| DELETE | 삭제 | Delete | O |

### 멱등성(idempotence)이 실무에서 중요한 이유

"같은 요청을 여러 번 보내도 서버의 최종 상태가 같은가?"

- `DELETE /orders/3`을 5번 보내도 3번 주문은 없는 상태로 동일 → 멱등
- `POST /orders`를 5번 보내면 주문이 5개 생김 → 멱등하지 않음

그래서 **결제 버튼에 중복 클릭 방지가 필요한 것**이고, 네트워크가 불안할 때 GET은 재시도해도 되지만 POST는 함부로 재시도하면 안 된다. 프론트에서 `isPending` 같은 플래그로 버튼을 막는 게 단순한 UX 문제가 아니라 데이터 정합성 문제라는 걸 이번에 이해했다.

## 5. Status Code — 백의 자리만 봐도 절반은 안다

```
1xx  받았고 처리 중
2xx  성공
3xx  다른 데로 가라
4xx  네 요청이 잘못됐다      ← 프론트가 고칠 문제
5xx  내 서버가 잘못됐다      ← 백엔드가 고칠 문제
```

**4xx인지 5xx인지 먼저 보는 습관**만 들여도 "제 코드가 문제인가요 서버가 문제인가요"로 시간 쓰는 일이 줄어든다.

| 코드 | 의미 | 프론트에서 보통 이렇게 처리 |
|---|---|---|
| 200 | 성공 | 데이터 렌더 |
| 201 | 생성됨 | 목록 갱신 / 상세로 이동 |
| 400 | 요청 형식 오류 | 입력값 검증 메시지 |
| 401 | 인증 안 됨 | 로그인 페이지로 보내기 / 토큰 갱신 |
| 403 | 권한 없음 | "접근 권한이 없습니다" 안내 |
| 404 | 자원 없음 | 빈 상태 화면 |
| 500 | 서버 내부 오류 | 재시도 안내 + 에러 리포팅 |

401과 403의 차이를 한 문장으로: **401은 "너 누군데?", 403은 "너인 건 알겠는데 안 돼."**

## 6. Postman으로 직접 쏴보기

브라우저 주소창으로는 **GET밖에 못 보낸다.** POST나 DELETE를 테스트하려면 별도 도구가 필요하고, 그게 Postman이다.

연습은 [JSONPlaceholder](https://jsonplaceholder.typicode.com) 같은 목 API로 했다.

```
GET  https://jsonplaceholder.typicode.com/posts/1
  → 200 OK, 게시글 객체 하나

GET  https://jsonplaceholder.typicode.com/comments?postId=1
  → 200 OK, postId가 1인 댓글만 배열로

POST https://jsonplaceholder.typicode.com/posts
  Body → raw → JSON
  { "title": "테스트", "body": "본문", "userId": 1 }
  → 201 Created, 서버가 부여한 id가 붙어서 돌아옴

GET  https://jsonplaceholder.typicode.com/posts/99999
  → 404 Not Found
```

직접 404를 **일부러 내보는 것**이 은근히 도움이 됐다. 에러 응답도 정상적인 응답의 한 종류라는 감각이 생긴다.

> Postman 웹 버전은 CORS 때문에 별도 에이전트가 필요할 수 있어서 데스크톱 앱이 편하다.

## 셀프 체크

<details>
<summary>1. "프론트엔드 개발자는 서버와 무관하다"는 말이 틀린 이유는?</summary>

프론트엔드 코드도 빌드 결과물이 웹 서버에 배포되고, 사용자의 브라우저(클라이언트)가 그 서버에 요청해서 받아간다.
클라이언트/서버는 역할 구분, 프론트/백엔드는 코드 영역 구분이라 서로 다른 축이다.
</details>

<details>
<summary>2. <code>/users/42</code>와 <code>/users?id=42</code> 중 어느 쪽이 맞나?</summary>

자원 하나를 특정하는 것이므로 `/users/42`(Path Variable)가 맞다.
쿼리 스트링은 목록에 조건을 거는 용도다. 빼면 의미가 성립하지 않는 값은 Path에 둔다.
</details>

<details>
<summary>3. POST가 멱등하지 않다는 게 UI 설계에 주는 영향은?</summary>

같은 요청이 두 번 가면 데이터가 두 개 생긴다. 그래서 제출 버튼은 요청 중에 비활성화해야 하고,
네트워크 오류 시 자동 재시도를 넣을 때도 GET과 달리 POST는 함부로 재시도하면 안 된다.
</details>

<details>
<summary>4. 401과 403의 차이는?</summary>

401 Unauthorized는 인증이 안 된 상태(토큰 없음/만료) — 로그인하면 해결될 수 있다.
403 Forbidden은 인증은 됐지만 권한이 없는 상태 — 로그인해도 해결되지 않는다.
</details>

<details>
<summary>5. 폴링 대신 웹소켓을 쓰는 이유를 비용 관점에서.</summary>

폴링은 변화가 없어도 주기마다 요청이 발생해 서버 부하와 트래픽이 낭비된다.
웹소켓은 한 번 연결을 맺어두고 서버에 이벤트가 생겼을 때만 전송하므로, 헛요청이 사라지고 지연도 줄어든다.
</details>
